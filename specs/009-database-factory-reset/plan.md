# Implementation Plan: Database Factory Reset and System Purge

**Branch**: `009-database-factory-reset` | **Date**: 2026-10-02 | **Spec**: [spec.md](file:///home/rhoribe/lab/minhashoras/specs/009-database-factory-reset/spec.md)

**Input**: Feature specification from `specs/009-database-factory-reset/spec.md`

## Summary

Implement a secure, administrator-controlled factory reset capability that wipes all operational records (`overtime_records`, `compensation_schedules`, `access_audit_logs`, `user_sessions`) and optionally purges server backup files, while safely preserving a baseline administrator account to prevent lockout. On the frontend, provide a high-visibility danger zone tab with a confirmation modal requiring typing "ZERAR", and purge client Dexie storage and local storage to prevent ghost synchronization.

**Project Type**: Web Application (Fastify REST backend + Vue 3 SPA/PWA frontend)  
**Performance Goals**: Factory reset atomic execution < 3 seconds; API response time < 500ms  
**Constraints**: Baseline memory < 200MB, touch targets >= 44x44px, zero ghost sync of pre-reset offline data  
**Scale/Scope**: Self-hosted single-node deployment  

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

- **Principle I: Mobile-First & Cross-Platform PWA**:
  - *Pass*. Danger zone card, reset trigger button, and confirmation modal are built with responsive layouts and touch targets >= 44x44px (`min-h-[44px]`).
- **Principle II: Offline-First Operation & Deterministic Sync**:
  - *Pass*. Local IndexedDB tables and sync queue are explicitly wiped upon reset. System epoch prevents stale offline records from corrupting the clean server state on reconnect.
- **Principle III: Minimalist Architecture & Resource Efficiency**:
  - *Pass*. No new heavy dependencies introduced. Uses existing Fastify, better-sqlite3 transactions, and Node.js `fs` module.
- **Principle IV: Reliable & Lightweight Database Persistence**:
  - *Pass*. Atomic SQLite transaction ensures that either all target tables are cleared and epoch updated, or none are. Database constraints and schemas remain intact.
- **Principle V: Containerized Single-Node Deployment**:
  - *Pass*. Fully compatible with single-node Docker setup and named data/backup volumes.
